**Readiness after the November 2026 integrity repairs**

This application is not established as a replacement for SAP S/4HANA, SAP IBP, or Kinaxis Maestro. The original investigation deliberately traced procure-to-pay and its shared persistence, valuation, identity and integration components. It did not certify every department. Fixing its findings does not establish that the unexamined areas are solid.

The code provides a substantial planning foundation: typed network data, forecasting, MRP/DRP, inventory policies, S&OP optimization, finite scheduling, promising, execution, purchasing, selling, valuation and reporting. Those capabilities and a large test suite are useful evidence of implementation. Enterprise readiness additionally requires authoritative business controls, representative operational performance and independent acceptance of business outcomes.

The changes retain the document/scenario model. They add enforced boundaries to the audited live-state transitions; they do not turn every stateless action into an independently persisted business command. The browser adopts server-normalized posting metadata after saves. Existing draft editing and place/family permissions remain supported.

Verification of the delivered source: **1,731 engine tests passed, four conditional checks skipped** in the full run without a PostgreSQL server. The final PostgreSQL-specific run passed **33 tests** (one SQLite-only connection check skipped), including all **19 new integrity regression cases**, concurrency, backup/restore and replay protection. The selected Playwright suite passed **24 tests**; the web build, Ruff, CI YAML parse and generated API-schema comparison passed. These suites overlap and their counts should not be added as unique tests. The independent persisted normal flow also reconciled 100 units at INR 10 plus 10% tax: stock 1,000 debit, input tax 100 debit, bank 1,100 credit, AP and GR/IR zero.

The container was built with a temporary build-only trusted-CA adaptation for the managed environment. Certificate verification stayed enabled; the session certificate was not committed to the repository or baked into image layers. The image built successfully. A nonroot runtime smoke test, with the hardened backend mounted read-only, returned health 200, blocked-payment 409 and forged-save 403. Subsequent restore/master-approval refinements are covered by the source regression suite; the image was not rebuilt after those refinements. No production deployment was performed.

Existing data may lack posting metadata or cancellation dates. Where a saved company's old posting basis is known, the save boundary fills metadata from that old basis before accepting relevant edits. An unknown historical cancellation date or missing external transaction evidence cannot be reconstructed honestly from source code. Existing inconsistent books require reconciliation; this repair does not silently manufacture historical facts.

**Architecture: sound choices and remaining boundaries**

A modular monolith, pure planning functions, a shared scenario model and version snapshots are reasonable choices for an interactive planning product. Microservices or a table per object would not, by themselves, make its business behavior correct. The current live-company aggregate still couples many departmental objects into one JSON document. Critical invariants therefore depend on comprehensive application checks at every mutation path.

The next architectural step is a clearer distinction between editable scenario/draft data and posted operational records. Operational commands should read authoritative state, authorize an operation, validate invariants and commit document effects, dated postings, audit and inbox/outbox state atomically. Planning computations should consume explicit immutable input revisions and return explainable results. This can be built within the existing modular monolith.

**Which competitor is the relevant target?**

SAP S/4HANA is an operational ERP comparison. SAP IBP is the closer planning comparison. Kinaxis Maestro is a planning/decisioning and concurrency comparison. Their scope should not be treated as interchangeable. SAP's [IBP feature overview](https://www.sap.com/products/scm/integrated-business-planning/features.html) and [response/supply planning overview](https://www.sap.com/products/scm/integrated-business-planning/features/response-and-supply-planning.html), and Kinaxis's [Maestro platform overview](https://www.kinaxis.com/en/solutions/platform), define useful comparison areas. Vendor descriptions are not independent proof of relative performance.

The evidence does not support broad S/4HANA replacement or SAP/Kinaxis parity. A narrower market position—planning and operational decision support for a defined type of manufacturer/distributor—could be credible, subject to a representative pilot. That is a product hypothesis, not a tested competitive conclusion.

Choose one customer process and workload first. Record an exact reference product/version/configuration; prepare an independently approved transaction/ledger corpus; compare exceptions and reversals as well as the normal case. Measure planning quality, response time, concurrency, memory, recovery and usability against an incumbent or the customer's current process. Procurement, warehouse, finance and planning owners should each accept the expected results. This produces defensible evidence of where the app wins or loses without a fictional percentage-parity score.

**Recommended next investigation**

Prioritize order-to-cash as the next deep audit because its sales, delivery, credit and payment state shares the same company aggregate and financial reporting machinery. Trace one order through credit release, stock issue, invoicing, payment, return and correction. Attack raw save/patch/merge/restore/integration routes, inject failure boundaries, and reconcile per entity and date. Extend to manufacturing/WIP and transport settlement when the trace identifies shared risks. These are unverified areas, not declarations that the implementations are defective or complete.
